## 1. Project context (decisions from earlier sessions)

- **Long-term vision (B):** Conversational AI Robot — natural conversation, context, actions.
- **First MVP (A):** Voice-command robot — listen, recognize simple commands, perform motion, respond.
- **Start from Smart Audio** rather than rebuilding Bluetooth/Wi-Fi first.
- **Logical architecture:** Audio Manager, AI Manager, Motion Manager, Robot Orchestrator. Build subsystem functions first; introduce minimal Orchestrator when integration requires it. Avoid giant manager classes.
- **Language:** C++17 for core software; Python/Bash for tooling. Pi as Linux target; other firmware languages chosen when motion hardware is defined.
- **Milestones:** M0 architecture/build foundation → M1 Audio → M2 AI voice commands → M3 minimal Orchestrator + Motion Simulator → M4 physical Motion → M5 integrated MVP.

## 2. Decisions reached today

### A. Skills, references, scripts

- **Skills** explain *when/how* Agent should perform a workflow; keep main `SKILL.md` short.
- **On-demand reference `.md`** files hold extra instructions for situations that actually need them (design, debugging, etc.), avoiding irrelevant context on small tasks.
- **Reusable scripts** execute repeatable tasks deterministically: build, test, sync/deploy to Pi, run, collect logs. Script must work without Agent, validate inputs, return useful exit codes and output.
- Create scripts and references **as the need appears**, not a speculative framework in advance.

### B. MCP

- **MCP** is a protocol, not another Codex app; an MCP server exposes tools/resources/prompts to an AI client.
- **No MCP server needed now.** Codex with terminal access can invoke scripts/SSH directly. Revisit only if cross-client standardization, shared remote tool access, or access-control requirements justify it.

### C. Multiple Codex chats

- Two active Codex chats can be two independent **agent sessions**; that does not automatically make them a coordinated multi-agent system.
- For concurrent coding, prefer separate Git worktrees/branches; avoid two agents changing the same working tree or deploying to the same Pi simultaneously.
- **V1 default:** one main Codex session per feature.

### D. Phase 3 — Run & Debug (important learning guardrail)

- **Human-led debugging, AI-assisted execution** for substantive technical bugs.
- Agent can build/run/test and collect facts and logs; **user leads hypotheses, chooses experiments, checks root cause, reviews the fix**.
- Trivial issues (obvious path/format problems) may be handled automatically with a concise report.
- For technical/critical faults, don't let Agent silently iterate fixes until PASS; pause at an investigation decision point. Safety-critical operations need explicit approval.
- Feature closure includes explaining symptom → hypothesis → evidence → root cause → fix → verification, in the user's own words.

### E. Development environment / Raspberry Pi

- **Source of truth:** Git repository in **WSL Linux filesystem** on Windows.
- **Codex runs in WSL**; when needed, it can use approved terminal commands and scripts to connect to Raspberry Pi by SSH.
- **Early build strategy:** sync source (`rsync`/`scp`) → **build natively on Pi** (CMake) → test/run → collect logs to WSL. Cross-compilation can come later if needed.
- Pi SSH access requires correct networking, keys/credentials, permissions and possible sandbox approvals; no credentials in Git. Scripts should avoid destructive operations or unreviewed `sudo`.
- **No MCP necessary** for this arrangement.

## 3. What we are intentionally NOT doing now

- Not implementing MCP server, complicated skills, multi-agent orchestration, or full robot framework.
- Not building all three managers / the Orchestrator in M0.
- Not expanding Bluetooth/Wi-Fi or designing all AI/Motion features before Audio works.
- Not spending more sessions discussing architecture without a concrete blocker.
